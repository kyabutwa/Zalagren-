# Zalagren Service Catalog Contract

## Purpose

The catalog defines what Zalagren can coordinate as a service. It does not create providers, prices, availability, authorization or regulatory status.

## Admission rule

A service may become operational only when its real-world prerequisites are represented and evidenced.

### Required chain

Participant → Context → Need/Intent → Service → Provider/Capability → Eligibility → Proposal → Authorization → Request → Action → Event → Evidence → Resolution.

### Intelligence services

CONSTANTYNA and GENESIS are Zalagren intelligence capabilities. They may explain, research, compare, propose and coordinate governed workflows, but neither can grant itself authority or execute protected actions without the Core authorization path.

### Prohibited assumptions

The catalog must never infer:
- provider qualification from listing alone;
- authorization from relationship;
- payment completion from request submission;
- service completion from provider acceptance;
- legal/regulatory approval from onboarding;
- data-protection compliance from account creation;
- availability from the existence of a service definition.

## Service truth states

🔵 PROPOSED — designed but not implemented.

🟡 SUPPORTED — implemented but not fully verified in production.

🟢 VERIFIED — provider, workflow, integration and production evidence verified.

🔴 FAILED — attempted operational path currently does not work.

A catalog definition without a verified provider workflow is not a 🟢 VERIFIED live service.
